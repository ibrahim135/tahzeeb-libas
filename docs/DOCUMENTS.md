# PDF documents (Phase 5)

Version 0.5.0 adds offline English A4 documents. Set shop name, address, contact
and customer receipt notes in Settings → Shop details. Shop name is required;
other fields are optional. Saving uses an expected-timestamp guard so an old
editor cannot overwrite a settings import or newer edit. Settings remain fully
included in workbook schema v1; the SQLite schema stays v1.

Open a saved bill and choose Payment receipt in PAYMENT or Warehouse measurement
slip in MEASUREMENTS. Opening reads order, customer and shop details in one
transaction. Preview, Save, Share and Print use the same generated bytes. A Shop
copy switch regenerates the same saved snapshot with a different copy label.
Refresh from saved bill deliberately loads any newer saved details. PDFs are
outputs, not separately persisted business records, and old saved files do not
change when a bill changes.

## Content and privacy

The customer receipt includes bill/customer identification, dates, delivery
status, garment descriptions/variants/quantities, exact integer-paise rates and
charges, subtotal, discount, total, received, balance and derived payment status.
It lists active payments with their original dates and methods. Corrected/voided
entries are excluded from received totals; the complete correction audit remains
in the app and Excel backup. Order notes and shop receipt notes are printed.
Private customer notes and individual payment notes are excluded.

The warehouse projection includes shop identity, bill/customer name and phone,
delivery date/status, descriptions/variants/quantities, enabled upper/lower
sections in inches, exact decimal values and fitting instructions. Empty enabled
sections say that values were not entered; items configured with no standard
measurements explain that sizes/details belong in description/notes. Upper and
lower length/hips remain separately labelled. No rates, discounts, totals,
payments, balances, customer address/private notes, general order notes or shop
receipt notes are passed to warehouse layout. Descriptions/fitting instructions
are printed as entered, so avoid putting financial information in those fields.

## Layout and platform integration

Both formats use separate content projections and a shared A4 layout engine.
Noto Sans Regular/Bold, including INR, are embedded from bundled assets under
SIL OFL 1.1 (see assets/fonts/). No runtime font download, backend or Internet
operation is used. English is the agreed document language; unsupported glyphs
produce a clear error rather than silently disappearing. Saved records are not
modified on generation failure.

Text explicitly spans pages, including multiline instructions, long descriptions
and unbroken words. Headings request room for subsequent content. Continuation
pages repeat bill identification and all pages have page numbers. Generation
runs in a worker isolate. A runtime header guard rejects more than 2,000 pages;
partial files are never offered. Documents do not use unbreakable garment cards
or tables for long notes.

Preview uses Android's PDF rasterizer through printing. Saving uses the normal
system document dialog; sharing uses share_plus and app-private temporary copies
retained for seven days to allow receivers to read them. The next share cleans
old copies. A share-sheet result does not prove the receiving app saved a file.
Printing uses Android's print service with frozen A4 bytes; choose multiple
copies in its dialog. Printer/service availability and physical output are
separate from successful PDF generation. No direct Bluetooth integration or
broad storage permission is added. Native rasterizer failure leaves Save/Share/
Print available; cancellation is distinguished from success.

## Repeatable checks

Run `flutter analyze` and `flutter test`. New tests cover exact totals and active
payment corrections, missing/upper/lower/both/no measurements, financial privacy,
variants/leading-zero phones, bundled INR glyphs and embedded font maps, long
multiline/single-word text, more than 20 pages, unsupported text, settings stale
edits/streams/Excel preview invalidation/file reopen, compact PDF actions and
unsaved shop editing. Print/raster actions are mocked for widget tests; those
tests do not certify native printing.

Optional independent PDF inspection with Poppler (not required for the portable
Flutter test suite):

```sh
TAHZEEB_PDF_SAMPLES=/tmp/tahzeeb-pdf-samples flutter test test/document_test.dart
python3 scripts/inspect_document_samples.py /tmp/tahzeeb-pdf-samples
pdftotext -layout /tmp/tahzeeb-pdf-samples/receipt_original.pdf -
pdftotext -layout /tmp/tahzeeb-pdf-samples/warehouse_original.pdf -
pdftotext -layout /tmp/tahzeeb-pdf-samples/warehouse_long.pdf -
pdftoppm -scale-to 1200 -png -singlefile /tmp/tahzeeb-pdf-samples/receipt_original.pdf /tmp/tahzeeb-pdf-samples/receipt
```

These files contain synthetic fixtures only. Check every instruction from 0 to
799, the 200 repetitions of LONGTOKEN and FINAL_WAREHOUSE_INSTRUCTION in the long
slip. Check receipts include the INR amounts and both copy labels, and warehouse
outputs exclude the financial/private tokens from the test fixture. Inspect page
images and A4 page dimensions; text extraction alone does not prove layout.

## Phone checks still required

Update the existing installation with the same signing key and app ID. Retain a
backup outside the phone. Edit shop details, reopen the app and generate both
formats from a multi-garment historic bill with corrected and partial payments.
Verify previews, INR, fitting instructions, dates and both copy labels. Save to a
local Android document provider, cancel/retry, open the saved files offline and
share them to a chosen receiving app. Check physical printing and multiple copies
through an installed Android print service; record phone/Android/printer details.
Repeat with long notes/multiple pages and check the final instruction. No Android
target was attached to the cloud during Phase 5, so these remain device checks.
